# Notes

*(Freeform, persistent observations for future-me — recurring patterns, teaching adjustments, things worth remembering across many sessions that don't belong in state.md's single-session snapshot or roadmap.md's checklist. Append or edit in place; no fixed structure.)*

- **"Solved" means worked through live, not "a file exists that runs."** Learned this the hard way on 2026-07-02: the roadmap said 9 patterns were mastered based purely on solution files existing in the repo, but Lawrence had never actually gone through them with the mentor — they were imported/inherited, not personally derived. Roadmap was reset to 0/17. Going forward, only mark a pattern `[x]` after a real session where Phase 2's discipline was followed live (brute force stated, optimized, complexity re-derived, edge cases covered, run in LiveCoding). Never infer mastery from git history or file presence again.
- **Verify understanding, not recall, once real practice starts.** This is still the right instinct for DP recurrences and anything else that's easy to pattern-match from having seen a solution before — probe with "why," not just "what."
- **Write everything — UI copy and live chat explanations — in plain, simple English.** Learned 2026-07-02 while building Phase 0's interactive module: the first draft of Section 5 used dense phrasing ("auxiliary structure," "space complexity is whichever one dominates," "pushed/popped onto the stack") and Lawrence explicitly asked for it to be rewritten in easier English. Short sentences, everyday words, numbered points over dense multi-clause sentences. Default to this the first time, don't wait to be asked.
- **Interactive teaching sections need a way forward at the bottom, not just the top.** Learned 2026-07-02: Phase 0's section nav pills live at the top of the page; the first version of each section ended with plain text like "Next: Section 2" with nothing to click, so Lawrence finished reading, hit the bottom, and had no way to continue without scrolling back up. Fixed by giving every section a real "Continue to Section N →" button at the bottom that switches sections and scrolls to top. Apply this to any future interactive/multi-section teaching UI, not just Phase 0.
- **Don't linger in Q&A once Lawrence answers correctly.** Said directly 2026-07-02 during the Contains Duplicate check-in: "you will not waste time chatting with me here, make the next step." The Phase 2 discipline (brute force → optimize → complexity → edge cases) still gets verified with questions every problem — but the moment his answers are correct, confirm briefly and move straight to assigning/building the next step. No extra rounds of follow-up once he's right.
- **He now keeps his brute-force attempt as commented-out code above the optimal solution, instead of deleting it.** Adopted 2026-07-02, after his Contains Duplicate brute force got deleted before the file was reviewed, which triggered an unnecessary "did you skip brute force?" callout — he had done it, just hadn't kept it. Check the file for a commented-out brute-force block before assuming the step was skipped; don't make him re-explain it verbally if it's already there.
- **Bulk-imported solution files often already contain the full answer.** All 47 reference files in LiveCoding were imported from an old project, and several (containsDuplicate, twoSum, validAnagram so far) had complete working solutions already written in, which would spoil the reveal-gated Phase 1 workflow if left as-is. Stub any file (problem comment + empty method + test calls only) before pointing Lawrence at it for a real session — assume it's baked until checked. Documented in `CLAUDE.md` too since it's an infra-level gotcha, not just a teaching note.
